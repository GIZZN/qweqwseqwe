# Что нужно реализовать на сайте, чтобы авторизация десктопа работала идеально

Десктоп-приложение само ничего не «проверяет» в вакууме — вся доверенная проверка
живёт на сервере. Ниже полный контракт эндпоинтов, которые дёргает приложение, и
что именно сервер обязан возвращать. Базовый адрес: `NEXT_PUBLIC_API_URL`
(в проде `https://diplom-chi-ten.vercel.app`).

Помечено **[NEW]** — то, чего ещё нет и без чего новая (усиленная) проверка
авторизации не активируется. Остальное уже используется текущим флоу входа.

---

## 1. Поток входа (pairing) — уже используется

### `POST /api/auth/app/init`
Старт привязки. Тело пустое.
- **200** → `{ "token": "<одноразовый pairing-токен>" }`
- Токен живёт ограниченное время (рекомендую 5–10 мин), одноразовый.

### Браузерная страница `/auth/app?token=<token>`
Открывается в системном браузере. Пользователь логинится на сайте (если ещё нет
сессии) и подтверждает вход в приложение. После подтверждения сервер привязывает
к `token` выданный **JWT** и профиль пользователя.

### `GET /api/auth/app/check?token=<token>`
Поллинг из приложения (раз в ~1 c, с backoff). Должен возвращать строго:

| Состояние | Ответ |
|---|---|
| Ждём подтверждения | **200** `{ "status": "pending" }` |
| Подтверждено | **200** `{ "status": "approved", "jwt": "<JWT>", "refresh_token": "<opaque>", "user": { … } }` |
| Токен истёк | **200** `{ "status": "expired" }` **или** HTTP **410** |
| Токен неизвестен/уже использован | **200** `{ "status": "invalid" }` **или** HTTP **404** |
| Временный сбой | **5xx** или **429** (приложение продолжит поллинг с backoff) |

Объект `user` (минимум `id` и `name`, остальное опционально):
```json
{ "id": "string", "name": "string", "email": "string", "avatar": "url?", "created_at": "ISO?" }
```
⚠️ После `approved` токен должен стать одноразовым (следующий `check` по нему может
вернуть 404 — приложение это уже корректно игнорирует, т.к. вход уже выполнен).

`refresh_token` — длинноживущий **opaque**-токен (НЕ JWT) для продления сессии без
повторного входа (см. раздел 4а). Если не выдать его, приложение просто не сможет
авто-продлевать JWT и разлогинит пользователя по истечении `exp`.

## 2. **[NEW]** Серверная ревалидация сессии — ГЛАВНОЕ

### `GET /api/auth/me`
Заголовок: `Authorization: Bearer <JWT>`.

Приложение зовёт этот эндпоинт **при каждом старте** (и доверяет ему как источнику
истины о том, жива ли сессия). Логика на стороне приложения — **fail-open**: сессию
сбрасывает ТОЛЬКО явный **401/403**. Поэтому контракт обязан быть точным:

| JWT | Ответ | Что сделает приложение |
|---|---|---|
| Валиден (подпись ок, не истёк, не отозван) | **200** (тело любое, лучше `{ "user": {…} }`) | оставит сессию |
| Невалиден / истёк / отозван | **401** (или 403) | мгновенно разлогинит, покажет «Сессия истекла» |
| Сервер недоступен / 404 / 5xx | что угодно кроме 401/403 | оставит сессию (офлайн-режим) |

Пока этого роута нет — приложение получает 404 и **безопасно остаётся залогиненным**
(fail-open), т.е. жёсткой проверки на старте просто нет. Как только роут появится —
проверка активируется автоматически, релиз приложения не нужен.

**Минимальная реализация:** взять Bearer, проверить подпись и `exp`, проверить, что
сессия/пользователь не отозваны → 200, иначе 401.

---

## 3. JWT — требования к токену

Приложение **на клиенте декодирует `exp`** из JWT (без проверки подписи), чтобы не
считать заведомо протухший токен живым ещё до обращения к серверу. Поэтому:

- Токен в `approved` ДОЛЖЕН быть настоящим **JWT** (`header.payload.signature`,
  base64url) с числовым полем **`exp`** (секунды от эпохи) в payload.
- Желательно также `iat` и идентификатор пользователя (`sub`/`uid`).
- Если выдаёте непрозрачный (opaque) токен без `exp` — клиентская ранняя проверка
  просто не сработает (fail-open), но `/api/auth/me` всё равно обязателен.
- **Отзыв (logout / смена пароля / бан)** должен приводить к тому, что
  `/api/auth/me` начнёт отдавать 401 по этому токену (храните jti/версию сессии
  на сервере, либо короткий `exp` + refresh).

## 4а. **[NEW]** Продление сессии — `POST /api/auth/refresh`

Чтобы пользователя десктопа «не выбивало», приложение само продлевает короткий JWT
по refresh-токену: **проактивно** за ~90 c до `exp` и **реактивно** при первом
`401/403` от `/me` или `/desktop/sessions` (один повтор с новым JWT, потом — логаут).

### Запрос
```
POST /api/auth/refresh
Content-Type: application/json
{ "refresh_token": "<opaque>" }
```
- Refresh-токен передаётся **в теле**, не в URL (чтобы не попадал в логи/историю).
- В проде идёт через нативный Rust-прокси; заголовок `Authorization` НЕ требуется.

### Ответы (строго)
| Состояние | Ответ | Что сделает приложение |
|---|---|---|
| Успех | **200** `{ "jwt": "<new JWT>", "refresh_token": "<new opaque>" }` | Сохранит новый JWT (+ ротированный refresh), перевзведёт таймер от нового `exp` |
| Refresh невалиден/отозван/протух | **401** или **403** | Считает сессию мёртвой → **разлогин** (нужен повторный pairing-вход) |
| Временный сбой / роут не задеплоен | **5xx / 0 / 404** | Fail-open: оставит текущую сессию, повторит позже |

### Требования безопасности (это важно для десктопа)
- **Ротация при каждом использовании** (refresh-token rotation): на успехе выдавать
  **новый** `refresh_token`, старый — немедленно инвалидировать. Приложение сохраняет
  новый и шлёт single-flight-запросы (две параллельные ротации друг друга не убьют).
- **Reuse detection**: если пришёл уже использованный (старый) refresh-токен — это
  признак кражи; отзови **всю цепочку/семью** токенов этой сессии и верни 401.
- **Срок жизни**: JWT — короткий `exp` (напр. 15–60 мин); refresh — длинный (напр.
  30–90 дней), желательно «скользящий» (продлевать при каждой ротации).
- **Привязка**: refresh-токен привязан к сессии устройства; `logout`/бан/смена пароля
  должны его отзывать. Храните на сервере хэш токена + `jti`/версию сессии.
- Refresh-токен — **opaque** (случайная строка), не JWT, чтобы не валидировать подпись
  на клиенте и легко отзывать на сервере.

## 4. Прочие эндпоинты, которые зовёт приложение

### `POST /api/auth/logout`
`Authorization: Bearer <JWT>`, тело `{}`. Должен инвалидировать **и JWT-сессию, и
связанный refresh-токен** на сервере (после этого `/api/auth/me` → 401, а
`/api/auth/refresh` по старому refresh → 401). Ответ не критичен (приложение чистит
локальную сессию и refresh в любом случае), но желателен **200**.

### `POST /api/desktop/sessions`
`Authorization: Bearer <JWT>`. Синк событий ассистента. Тело:
```json
{
  "type": "chat_message | live_answer | screen_analysis",
  "question": "string (<=1000)",
  "answer": "string (<=5000)",
  "model": "string",
  "response_time_ms": 0,
  "tokens_used": 0,
  "session_id": "string",
  "created_at": "ISO"
}
```
- Валиден → **200/201**.
- Токен протух/отозван → **401/403** — приложение поймает это и **автоматически
  разлогинит** (через событие `auth:expired`). Это второй (после `/me`) триггер
  авто-логаута, поэтому 401 здесь возвращать обязательно, а не глотать.

## 5. CORS (важно только для dev-сборки)

- **Прод**: запросы идут через нативный Rust-прокси (`http_proxy_get/post`,
  `ai_proxy_request`) — CORS не нужен, webview-ограничения обходятся.
- **Dev** (`npm run dev`): фолбэк на обычный `fetch` с `mode: 'cors'`. Чтобы вход и
  ревалидация работали в деве, на всех перечисленных роутах нужны заголовки:
  ```
  Access-Control-Allow-Origin: <origin tauri dev, напр. http://localhost:1420> (или *)
  Access-Control-Allow-Headers: Authorization, Content-Type
  Access-Control-Allow-Methods: GET, POST, OPTIONS
  ```
  и обработка preflight `OPTIONS`.
